## 1. 发版产物与当前实现

“发版”不是单独上传一个安装包，而是同一版本的多个面向同步到位：

| 面向 | 当前来源 | 发布要求 |
|---|---|---|
| 源码与版本 | Git 提交、`vX.Y.Z[-beta.N]` tag | tag 必须指向已进入 `main` 的提交 |
| 桌面安装包 | `.github/workflows/build-desktop.yml` | Windows x64 和 macOS arm64 在各自目标平台构建，并运行 `verify-packaged.mjs` |
| GitHub Release | 人工创建并上传 CI 产物 | 发布标题、发布文案、Pre-release 状态和资产必须一致；历史 tag 例外需记录映射 |
| 站内更新日志 | `apps/web/content/changelog.md` | 必须遵守现有解析器格式；合并到 `main` 后触发官网部署 |
| 官网下载页 | `packages/site-ui/src/use-latest-release.ts` | 展示的版本必须对应真实 Release；未接通的文件不能标成可下载 |
| Obsidian 插件 | `apps/obsidian/manifest.json` 与构建产物 | 独立版本；只有本次实际发布时才出现在 Release 资产和文案中 |
| 浏览器扩展 | `apps/extension/src/manifest.json` | 独立版本；当前不在桌面 release workflow 中自动打包 |

当前实现的边界：

- `build-desktop.yml` 由 `v*` tag 或手动触发，只构建并上传 GitHub Actions artifact。
- 当前 workflow **不会自动创建 GitHub Release，也不会自动上传 Release 资产**，这两步由发版负责人完成。
- `verify-packaged.mjs` 会从全新数据目录启动打包内的 API 与 Web，检查健康接口、rewrite、SSR 和状态目录自建；它不等同于安装器人工冒烟。
- `deploy-site.yml` 只在 `main` 相关路径变化时部署官网；仅推 tag 不会自动更新站内更新日志。
- 发版流程本身不新增运行时资源开销。构建阶段的 CPU、内存、磁盘和网络消耗仍由现有 GitHub Runner、Electron Builder 与依赖安装决定；若改变构建矩阵或依赖闭包，必须在方案阶段单独估算。

## 2. 版本与发布状态

产品版本使用 SemVer：

```text
MAJOR.MINOR.PATCH[-PRERELEASE]
v0.1.3
v0.1.0-beta.1
v0.1.0-beta.2
```

| 变更性质 | 版本变化 |
|---|---|
| `1.0.0` 之后不兼容的数据、配置或使用方式变化 | `MAJOR` |
| 向后兼容的用户能力；`0.x` 阶段的不兼容变化 | `MINOR` |
| 向后兼容的修复、打包或文案修正 | `PATCH` |
| 同一基础版本的连续测试发布 | `-beta.1`、`-beta.2`，并勾选 **Pre-release** |

版本规则：

1. GitHub Release 标题只使用版本号。预发布标题使用 `vX.Y.Z-beta.N`，例如 `v0.1.0-beta.1`、`v0.1.0-beta.2`；不追加产品名或变化说明。
2. 桌面安装包版本以 `apps/desktop/package.json#version` 为准；内置 Web 必须与它一致。
3. Obsidian 插件和浏览器扩展分别以自身 manifest 为准，不得因为产品发版就假装它们也升级了。
4. 新发布的 tag、显示标题和 package version 使用同一个版本标识。`beta.N` 必须勾选 GitHub Release 的 **Pre-release**。
5. 不覆盖已发布 tag，不上传同名但内容不同的资产。坏 beta 通过下一个 `beta.N` 修复，正式版通过新 `PATCH` 修复；确需撤下时保留 tag 和审计记录。
6. 发布前必须确认 changelog、package version、tag、产物文件名和官网展示版本能够互相对应。
7. 历史 tag 不改名。已有 `v0.1.0`、`v0.1.1`、`v0.1.2` 分别映射到标题 `v0.1.0-beta.1`、`v0.1.0-beta.2`、`v0.1.0-beta.3`；该映射只用于冻结的历史发布，后续发版必须让 tag、标题和版本号一致。

发布类型：

| 类型 | 用途 | 最低要求 |
|---|---|---|
| 产品发版 | 桌面工作台及配套文档 | 版本同步、双平台产物、GitHub Release、站内更新日志 |
| 预发布 | 小范围验证或安装器修复 | 同产品发版，并明确 Pre-release、限制和回退方式 |
| 组件发版 | 仅 Obsidian 或扩展 | 组件版本变化、安装说明、独立资产；不伪造桌面版本 |
| 站点部署 | 仅官网内容变化 | 不创建 tag 或 GitHub Release；确认不涉及客户端版本 |

## 3. 发布文案格式

### 3.1 三层文案

| 文案 | 位置 | 读者 | 作用 |
|---|---|---|---|
| Release 摘要 | GitHub Release 正文开头 | 用户 | 一句话说明这次为什么值得更新 |
| 发布分类 | GitHub Release 与站内更新日志 | 用户 | 按“新增、改进、修复”等说明可见变化 |
| 内部发版记录 | 发布 issue 或内部任务 | 维护者 | 记录提交、测试、资产、操作人和回滚点 |

不要直接把 commit 列表当 Release Notes。commit 描述实现过程，发布文案描述用户结果。

### 3.2 通用写作规则

- 首句先写用户能感知的结果，再写原因；不使用“若干优化”“多个问题”这类无法验证的描述。
- 每个条目只表达一个变化，优先写“现在可以做什么”“什么问题不再出现”。
- 使用“九漾 Onda”作为产品名；`Tassello` 只用于仓库、包名和现有技术产物。
- 用户文案使用中文分类：`本次重点`、`新增`、`改进`、`修复`、`安全`、`兼容与升级`、`已知问题`。
- 没有内容的分类直接省略，不保留空标题。
- 涉及数据目录、配置、登录态、平台权限或最低系统版本时，必须有“兼容与升级”。
- 已存在但本次未修复的问题写入“已知问题”，并说明影响范围和规避方式。
- 不承诺尚未合并、未构建或未真机验证的能力。

### 3.3 站内更新日志的硬格式

站内页面由 `apps/web/app/(site)/changelog/page.tsx` 和 `apps/site/app/(site)/changelog/page.tsx`
直接解析 Markdown，只识别以下结构：

```markdown
## 2026-10-27 · v0.1.0-beta.1

> 一段面向用户的摘要。

### 新增

- 一条用户可见变化。

### 修复

- 一条具体修复。
```

约束：

- 版本条目必须是二级标题，日期在前，中间使用全角间隔符 `·`。
- 分类必须是三级标题；每个列表项必须使用 `- `。
- 条目下的普通段落、有序列表、表格、任务列表和代码块不会进入页面正文。
- 二级标题会生成页面锚点；发布后不要随意改名或改日期，确需修文时以勘误方式处理。
- 站内更新日志与 GitHub Release 的事实必须一致，可以精简措辞，不得一边写“已修复”而另一边写“待验证”。

## 4. 发版流程

### 4.1 冻结范围

1. 明确本次是产品发版、预发布、组件发版还是站点部署。
2. 固定目标版本、目标提交、支持平台和发布窗口。
3. 列出本次发布影响的安装包、Obsidian、扩展、官网、更新日志、下载链接和迁移逻辑。
4. 将不属于本次的改动留在后续版本，不在 tag 前临时扩大范围。

### 4.2 对齐版本与文案

1. 更新桌面与内置 Web 的产品版本，并核对组件自身版本。
2. 写 GitHub Release 正文和站内更新日志，禁止从 commit 标题直接拼接。
3. 检查所有“新增/修复/已知问题”都有对应验证证据。
4. 确认发布文案中的平台名称、文件名、下载入口和实际产物一致。

### 4.3 通过发布门禁

按 [`development-workflow.md#validation`](./development-workflow.md#validation) 执行对应验证，至少满足：

- `bun run typecheck` 通过。
- 本次涉及的 API、Vault、文件状态库、Obsidian、扩展和 Web 构建通过。
- 桌面双平台 CI 成功，两边的打包运行时自检都通过。
- 本次用户可见界面已在真实宿主或浏览器检查。
- 没有未审查的 diff、调试代码、构建产物误提交或未合并修正。
- 所有待发布提交已进入 `main`；需要整理的分支已按仓库规则 squash。

任一门禁未运行或失败，都不得在 Release Notes 中写“已验证”。

### 4.4 构建并发布

1. 从 `main` 的发布提交创建产品 tag。`but` 不提供 tag 子命令，此处按仓库约定使用 Git 兜底，并在最终记录中注明用了 `git tag`。
2. 推送 tag 或手动触发 `build-desktop`。桌面原生包必须由对应目标平台构建，不得从 macOS 交叉生成 Windows 包。
3. 等待 Windows x64 与 macOS arm64 任务完成，确认 `verify-packaged` 日志通过。
4. 下载并核对 Actions artifact：文件名包含目标版本，文件非空，平台和架构正确。
5. 人工创建 GitHub Release，选择已存在的 tag；预发布勾选 **Pre-release**。
6. 粘贴发布正文，上传经过核对的安装包；需要独立组件时同时上传其构建产物。
7. 从 Release 页面重新下载一次资产，在目标系统完成安装、首启和一次最小业务冒烟。

### 4.5 上线官网与更新日志

1. 将版本文案和更新日志合入 `main`，等待官网 deploy workflow 成功。
2. 检查更新日志标题、日期、分类和列表是否正常渲染。
3. 检查首页与下载页显示的版本是否来自目标 Release。
4. 检查桌面与插件的版本标签是否分别准确；不得把产品版本当成所有组件版本。
5. 检查下载按钮只链接到真实存在的资产；占位入口必须标成不可用，不能伪装成可下载。

<a id="post-release"></a>
## 5. 上线后核对

发布完成后逐项确认：

- 新发布的 GitHub Release 标题与 tag 一致；历史例外使用已记录的映射，Pre-release 状态、日期和正文正确。
- 首页、下载页、更新日志和 Release 指向同一个目标版本。
- 两个安装包均可下载，文件名与支持的平台/架构一致。
- 安装包在目标系统能启动，首启数据目录可用，API/Web 基础链路正常。
- Obsidian 与扩展的版本标签只对自己真实发布的版本生效。
- 发布内容没有泄露 token、Cookie、账号、内部路径或测试凭据。
- 已知问题、升级限制和回退方式对用户可见。

发现问题时先在 Release 正文补充“已知问题”和处置方式，再决定是否撤下下载入口；不要在用户不知情的情况下替换同一 tag 的资产。

<a id="rollback"></a>
## 6. 回滚

发布事故分三类处理：

| 情况 | 处理 |
|---|---|
| 文案、链接或版本展示错误 | 修正官网或 Release 文案，保留 tag；记录影响范围 |
| 安装包可下载但存在明确阻断问题 | 将 Release 转为 Pre-release/撤下下载入口，指向上一稳定版，并尽快发 `PATCH` |
| 数据迁移或配置变更造成破坏 | 停止继续分发，保留失败产物，按迁移回退方案恢复；不得用同一版本悄悄替换修复包 |

回滚必须记录：

- 触发原因和首次发现时间。
- 受影响平台、版本和用户操作。
- 已撤回的入口、已通知的范围。
- 上一可用版本或恢复路径。
- 修复版本、验证结果和防止复发的改动。

## 7. 模板

### 7.1 GitHub Release 模板

```markdown
> 一句话说明本次更新带来的主要结果。

## 本次重点

- 用户最需要知道的一到三项变化。

## 新增

- 现在可以……

## 改进

- 调整了……，用户会感知到……

## 修复

- 修复了……；触发条件为……。

## 安全

- 修复了……安全问题；受影响版本和升级要求为……。

## 兼容与升级

- 支持平台：macOS（Apple Silicon）、Windows x64。
- 数据与配置：无需手动迁移 / 需要执行……
- 升级方式：覆盖安装 / 重新安装……

## 已知问题

- 在……情况下仍会……；规避方式是……。
```

若没有某类内容，删除对应整段。`beta.N` 标题同时勾选 GitHub 的 Pre-release 状态。

### 7.2 站内更新日志模板

```markdown
## YYYY-MM-DD · vX.Y.Z-beta.N

> 一段面向用户的发布摘要。

### 新增

- 一条用户可见变化。

### 改进

- 一条可感知的体验变化。

### 修复

- 一条有明确触发条件的问题修复。

### 安全

- 一条需要用户知晓或升级的安全修复。

### 兼容与升级

- 支持的平台、数据迁移和升级注意事项。

### 已知问题

- 尚未解决但会影响用户的问题及规避方式。
```

### 7.3 内部发版记录模板

```markdown
| 字段 | 内容 |
|---|---|
| 目标版本 | vX.Y.Z-beta.N |
| 目标 tag | vX.Y.Z-beta.N；历史例外填写实际冻结 tag |
| 发布类型 | 正式版 / Pre-release / 组件发版 / 站点部署 |
| 目标提交 | <sha> |
| 提交范围 | <上一版本 tag>...<目标 tag> |
| 操作人 | <姓名> |
| 构建运行 | <workflow run URL> |
| 发布地址 | <GitHub Release URL> |
| 测试结果 | <通过项、未运行项、环境阻塞> |
| Release 资产 | <文件名、平台、架构、校验结果> |
| 回滚点 | <上一可用版本与恢复方式> |
| 遗留问题 | <已知问题或“无”> |
```
