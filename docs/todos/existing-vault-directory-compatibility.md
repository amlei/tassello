# 已有 Vault 的目录结构兼容

> 状态：后续设计事项，尚未定案。本文不构成当前实现依据。
> 关联架构：[Vault 内容模型](../design/architecture.md#content-model)、[Obsidian 插件](../design/architecture.md#hosts)。

## 背景

桌面端与 Web 是面向运营人员的内容工作台，Obsidian 插件则是面向 Obsidian 用户的单篇发布工具。第一阶段将两端独立设计：

- 运营端保有自己的文章、贴图、视频、音频分类目录，并为新建内容写入稳定元数据。
- Obsidian 插件只处理当前 Markdown，不扫描整个 Vault，也不管理运营端内容库。
- 两端通过本机后端的发布任务连接，不共享整库管理状态。

后续需要支持用户把运营端接入已在使用的 Vault。用户可能已经采用自己的目录结构，例如日记、项目、归档、模板和多级素材目录；产品不得因此要求移动、改名或重组现有文件。

## 当前实现事实

- Vault 扫描会递归查找所有 Markdown，并跳过 `.git`、`.obsidian`、`.onda`、`.tassello` 和 `node_modules`。
- 内容类型从 `tassello.type` 读取；缺失时当前回退为 `article`。
- 运营端新建内容固定写入 `articles/`、`images/`、`videos/`、`audios/`。
- 内容目录只有一个 `vaultPath`，可以在设置中选择。
- 项目不使用 SQLite；设置和运营状态存放在 `.onda` 文件状态库。

- `packages/server/src/documents.ts`

- `apps/web/features/settings/settings-dialog.tsx`

## 需要解决的问题

### 扫描范围

- 是否允许选择多个内容根目录，而不是默认扫描整个 Vault。
- 是否支持用户配置排除目录，避免模板、归档和旧草稿进入内容库。
- 不再匹配的文件应从内容库隐藏，还是标记为未纳入。

### 逻辑分类

- 物理目录不得成为唯一分类事实；已发布内容应以 `tassello.type` 为准。
- 缺少 `tassello.type` 的文件不得继续静默归为文章。
- 是否增加“未分类”状态和内容库入口。
- 是否允许用户配置“目录到内容类型”的映射，作为未写入元数据时的显示规则。
- 目录映射只用于展示，还是也作为用户确认后的分类写入来源。

### 运营端新建内容

- 四个固定分类目录是否继续默认位于 Vault 根目录。
- 是否需要单独的运营工作区根目录，例如 `Onda/`，避免与用户已有的 `articles/`、`images/` 冲突。
- 已发布文件被用户移动到任意目录后，运营端应继续按 frontmatter 识别，不要求移回分类目录。

### 已有内容纳入

- 用户把已有 Markdown 纳入运营端时，是否需要显式确认后再写入 `tassello` 元数据。
- 是否支持批量分类、逐篇分类或目录映射后批量确认。
- 扫描、打开和预览必须保持零写入；任何元数据补全都必须由明确动作触发。
- 需要定义文件已发布后再次丢失 `tassello.id` 时的身份恢复策略。

### 两端协作

- 运营端与 Obsidian 同时编辑同一文件时，继续使用文件指纹检测外部修改。
- Obsidian 插件不得因为打开文件或切换待发布类型而重写属性。
- 发布仍通过本机 Elysia API 创建快照和任务，不在任一客户端复制发布引擎。

## 初步约束

以下约束可以作为后续方案设计的起点，但仍需独立审查：

1. 不移动、不改名用户的既有目录和文件。
2. 扫描是只读操作，不自动修复或补齐 frontmatter。
3. `tassello.type` 优先于目录映射；目录结构不能覆盖显式类型。
4. 缺少类型的内容进入“未分类”，不得默认成文章。
5. 运营端新建内容继续使用固定分类目录；已有内容不要求进入这些目录。
6. 设置继续使用 `.onda` 状态文件和 Vault 内 Markdown，不引入 SQLite。
7. 扫描范围在解析 Markdown 前通过目录过滤收敛，避免对无关目录做 IO。

## 待评估方案

### 方案 A：单一 Vault 根目录

继续只配置 `vaultPath`，递归扫描整个 Vault；以三态分类规则展示内容：

1. 合法 `tassello.type`；
2. 用户配置的目录映射；
3. 未分类。

优点是实现简单，不改变现有设置结构。缺点是大型个人 Vault 会扫描大量非发布内容，需要依赖排除规则。

### 方案 B：Vault 根目录加多个内容根

新增 `contentRoots`，只扫描用户指定目录；运营端分类目录可位于其中一个内容根下。

优点是扫描范围明确，适合已有 Vault。缺点是需要处理重叠根目录、相对路径稳定性、移动目录后的身份变化和设置迁移。

### 方案 C：独立运营工作区

运营端只在 Vault 下的专用目录工作，例如 `Onda/articles/`，不主动接入用户其余笔记。

优点是边界最清楚，几乎不会干扰用户自己的 Obsidian 数据。缺点是无法直接管理用户已有内容，可能需要后续导入流程。

## 验收方向

- 用户接入已有 Vault 后，原目录和文件名保持不变。
- 扫描新增文件后不会产生任何 Markdown 写入。
- 无 `tassello.type` 的文件不会自动出现在四个类型分类中。
- 用户显式分类或发布后，类型写入 frontmatter，文件无需移动。
- 移动已发布文件后，运营端仍按 frontmatter 识别内容。
- 大型 Vault 可以通过扫描范围和排除目录限制资源占用。
- 运营端与 Obsidian 插件不会因打开同一文件而互相改写。

## 非目标

- 本次不实现已有 Vault 兼容。
- 本次不为已有内容自动生成分类、ID 或时间字段。
- 本次不引入 SQLite、索引数据库或跨应用 CRDT。
- 本次不改变 Obsidian 插件只处理当前文件的边界。
